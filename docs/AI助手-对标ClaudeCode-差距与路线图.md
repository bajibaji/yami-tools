# AI 助手 × Claude Code 能力差距与路线图

> 目的：把 Open Yami 内置 AI 助手做到「不弱于 Claude Code」的生产力水平。
> 本文件是唯一对照基准（SSOT），每轮迭代更新「现状 / 差距 / 下一步」三栏。
> 更新时间：2026-09-11（第 1 轮）

---

## 一、Claude Code 的生产力要素拆解（12 项）

| # | 能力 | 为什么它是生产力关键 |
|---|---|---|
| 1 | **流式输出** | 长任务里用户能看到「正在想什么、调用了什么工具」，而不是干等一个转圈 |
| 2 | **工具调用可视化** | 每次读文件/改文件/跑命令实时上屏，可中断、可追溯 |
| 3 | **会话持久化与恢复** | 关掉窗口、切机器、第二天继续，历史不丢 |
| 4 | **上下文预算管理** | 长会话自动压缩/摘要，不会因为爆上下文突然失忆 |
| 5 | **精确文件编辑** | 按行号读、按片段替换/插入，弱模型也能改对，不必整文件重写 |
| 6 | **检索能力（grep/glob）** | 先搜再改，而不是把大文件整份塞进上下文 |
| 7 | **待办清单（Todo）** | 多步任务有进度骨架，模型不会做一半跑偏 |
| 8 | **验证闭环** | 改完自动编译/校验，报错自动回读并修复 |
| 9 | **子代理委派** | 把「搜一遍全工程」这类脏活丢给子代理，主上下文保持干净 |
| 10 | **权限分级** | 只读自动、写入确认、危险操作强确认，可切「全自动」 |
| 11 | **回滚与审计** | 每次修改可回退，有变更清单和哈希证据 |
| 12 | **计划模式** | 大改动先出方案再执行，避免瞎改（**本工程裁决：不做**，用待办清单替代） |

### 已达标/领先项（保持）
- **写盘安全**：所有写操作先预览、带 `expectedSha256` 冲突检测、原子替换、自动备份 —— 比「直接改文件」更稳。
- **真实编译门禁**：脚本写入强制跑引擎自带 tsc，编译失败自动回滚。
- **三层控制**：工程文件（MCP）/ 编辑器动作（5967）/ 试玩输入（5966）全覆盖。
- **零依赖**：无 npm 依赖，断网可用。

## 五、第 3 轮（已完成，可验证）：编译失败自动修复闭环

「改完跑编译、不过就自己修」是这类工具最值钱的一环；这一轮把它做进宿主主循环。

| 交付 | 落点 | 验证方式 |
|---|---|---|
| 编译失败识别 | `ai-host.js` `compileFailureOf()` | 识别 `ok:false + compile.ok:false`，带出错误条数、首条 `文件:行号`、tsc 原文、是否已回滚 |
| 修复指令生成 | `repairMessage()` | 要求：先定位再改、**只做最小片段替换**、改完必须确认编译、同一报错两次不过就停下讲原因 |
| 主循环接线 | `continueSession()` | 同一轮内检测到编译失败 → 推 `notice` 事件 → 注入修复指令 → 继续（不再直接收工） |
| 用户确认路径同样生效 | `/approve` 分支 | 手动确认的写入编译失败也走同一套自动重修，不是只有自动模式才有 |
| 上限与如实失败 | `MAX_REPAIR_ATTEMPTS`（默认 2） | 修满仍不过 → `status='compile-failed'` + 最后一次报错 + 说明工程已回滚 |
| 修复预算重置 | `/chat` 入口 | 每条新需求重置 `session.repairs`，上一轮的失败不会拖累下一轮 |

测试：`tests/test-ai-repair.cjs` —— 用"先写坏、收到报错后改对"的假模型验证整条回路，并验证修不好时如实失败、工程不留半成品。

## 六、第 4 轮（已完成，可验证）：改动看得见 + 危险操作拦得住

游戏工程是"改错一次就崩档"的场景，所以审批环节必须让人**看见具体改了什么**、让不可撤销的动作**必须二次确认**。

| 交付 | 落点 | 验证方式 |
|---|---|---|
| 统一差异工具 | `runtime/yami-mcp/modules/diff.js` | `tests/test-mcp-approval-diff.cjs` 第 1 组：增删统计、定位块、上下文保留、无变化表述、超大差异截断 |
| 写盘预览带真实差异 | `edit_script` / `patch_resource` 的 dryRun | 同第 2 组：`diff` 含 `@@` 与 `+` 行、风险级别、`diffStat` |
| 前端差异渲染 | `ai-agent.js` `renderDiff()` + 审批卡片容器 | 逐行着色（新增绿/删除红/定位蓝 + `+N/-M`）；接线断言在 `tests/test-ai-agent.cjs` |
| 删除二次确认 | `delete_resource` + 一次性令牌 | 同第 3 组：高危标记、影响摘要、无令牌被拦（`ok:false` + `confirmRequired`）、伪造令牌被拒、令牌用过即失效 |
| 热更新清单补全 | `probe-core.js` `updateFiles` 增补 `diff.js` | `tests/test-autoupdate.mjs` 新增断言：**声明的清单必须覆盖 modules 下全部模块**（漏一个，别人热更新后 MCP 直接崩） |
| 热更新容错 | `performAutoUpdate` | 个别文件远端暂缺（推送落地前的窗口）不再让整次更新失败：跳过并记入 `missingFiles` 如实报告；但 `probe-core.js`/`manifest.json`/`server.js` 缺失时仍然中止 |

> 坑位记录：`edit_script` 原来的预览里已有一个 `diff` 字段（片段前后对照），会把新生成的统一差异**覆盖掉**，宿主只拿到 15 个字符。已改名 `fragmentDiff` 并写进注释。

## 七、第 5 轮（已完成，可验证）：改错能一键回退

让用户敢让 AI 改工程的前提不是"写得准"，而是"**改错能退回去**"。这一轮把备份从"存在但看不见"变成"看得见、点得到、退得回"。

| 交付 | 落点 | 验证方式 |
|---|---|---|
| 备份旁挂元数据 | `modules/file-ops.js`：每个 `.bak` 配一份同名 `.json`（路径/工具/时间/哈希/体积） | `tests/test-mcp-approval-diff.cjs` 第 4 组：备份内容 = 改动前内容、带时间与来源工具 |
| `list_backups` 工具 | `server.js` | 同上：列出可回退版本、时间、来源工具、体积 |
| `restore_backup` 工具 | `server.js` | 同上：默认退回最早一次、dryRun 预览差异、安全备份、**撤销的撤销**、manifest 禁止回退、无备份如实说明 |
| 前端【撤销】面板 | `ai-agent.js` `renderUndoList()` + `ai-undo` 样式 | 只列本对话改过的文件，一点回退并显示 `+N/-M`；接线断言在 `tests/test-ai-agent.cjs` |
| 宿主接口 | `/backups`、`/backup-undo` | `tests/test-ai-repair.cjs` 第 3 组：只列本对话文件、回退成功、回退后内容回到最初 |
| 审批门禁修正 | `ai-host.js` `FILE_MUTATIONS` | `edit_script` **此前不在写盘审批集合里**——走这个工具改脚本不会弹审批卡。已纳入，并新增第 5 组断言守着（确认模式下必须停在审批、审批前工程不得改动、取消后不得改动） |

> 坑位记录（两处真缺陷，都由测试抓到）：
> 1. `writeAtomic` 的备份路径从绝对改成相对后，`restoreBackup` 仍按绝对路径处理，导致**编译失败自动回滚静默失效**；
> 2. `edit_script` 漏在 `FILE_MUTATIONS` 之外，写盘绕过审批。

## 八、第 6 轮（已完成，可验证）：AI 能自己跑一遍试玩并报坏

通用编码助手永远做不到的一件事：**把游戏跑起来、走两步、再把运行时黑匣子的变化读回来**。这一轮把"改完到底还能不能玩"变成一条可自动执行的验证。

| 交付 | 落点 | 验证方式 |
|---|---|---|
| 动作脚本规整 | `modules/playtest.js` `normalizeSequence()` | `tests/test-playtest-smoke.cjs` 第 1 组：字符串简写、别名（ok→Enter）、按住时长按需下发、非法按键拒绝、步数上限、空脚本 |
| 诊断对比判定 | 同文件 `diffDiagnosis()` / `describeVerdict()` | 同第 2 组：无变化判 ok、新报错/变频繁/新卡住/性能恶化各自识别、结论话术可直接给用户 |
| `playtest_smoke` 工具 | `runtime-bridge.playtestSmoke()` + server 注册 | 同第 3、4 组：无试玩时安全降级并要求先启动试玩；空脚本拒绝；**完整成功路径**用模拟 5966 桥验证按键真的下发、前后各取一次诊断、识别新报错（带文件行号）与新卡住事件、给出前后性能快照 |
| 端口可覆盖 | `YAMI_RUNTIME_BRIDGE_PORT` | 让测试与真机共用同一套代码路径，不写死 5966 |
| 热更新清单 | `probe-core.js` 增补 `modules/playtest.js` | `tests/test-autoupdate.mjs` 的「声明清单覆盖全部模块」断言守着 |

## 九、第 7 轮（已完成，可验证）：改完说清"到底动了什么"

前六轮解决了改得准、看得见、退得回、跑得动；这一轮把收尾补上——用户不必自己比对就知道这次改了什么、验证到哪一步、下一步该做什么。

| 交付 | 落点 | 验证方式 |
|---|---|---|
| 快照对比 | `modules/changelog.js` `snapshotProject()` / `diffSnapshot()` | `tests/test-changelog.cjs` 第 1 组：修改/新建/删除识别、哈希不变即无变更 |
| 小结合成 | 同文件 `buildChangelog()` / `describeChangelog()` | 同组：统计正确、来源工具与编译结论标注、话术含编译与试玩结论、全回滚时如实说明 |
| `project_changelog` 工具 | `server.js`（含 `reset` 基线语义） | 第 2 组：建立/重置基线、识别真实变更、**写了又改回去不计入变更**、新建文件归类 |
| 写入记录 | `server.js` `rememberWrite()` | 小结里每个文件都带来源工具与编译结论；试玩后带 verdict |
| 收尾自动小结 | `ai-host.js` `attachChangelog()` | `tests/test-ai-repair.cjs`：净变更为 0（被回滚）时如实计 0、不伪造小结 |
| 前端小结卡片 | `ai-agent.js` `renderChangelog()` + `ai-changelog` 样式；打开面板自动建基线（`/changelog-baseline`） | 构建门禁 + 接线断言 |

## 十、第 8 轮（已完成，可验证）：把"逐条确认"从阻力变成可控授权

一件任务里同一个文件常要连着改好几次，每条都弹审批会把人磨烦；而"逐条确认"一旦变成走过场，反而更危险。
做法不是取消确认，而是让用户**显式授权**、并且随时能收回。

| 交付 | 落点 | 验证方式 |
|---|---|---|
| 授权判定 | `ai-host.js` `isGranted()` / `addGrant()` | `tests/test-ai-repair.cjs` 第 5 组：首次仍需确认 → 勾选后批准 → 同文件同工具不再打断 → 撤销后恢复逐条确认 |
| 授权持久化 | 会话落盘带 `grants`，恢复会话时带回 | 同上（授权随会话保存，重开窗口仍生效） |
| 授权查询与撤销 | `POST /grants`（列出 / `revoke` 单个 / `clear` 全部） | 同上：`/grants` 列出带工具中文名与文件；撤销后重新逐条确认 |
| 删除类免疫 | `DELETE_TOOLS` 判定 | 同上末条：授权列表与方法都不接受 `delete_resource`（不可轻易撤销的动作必须逐条确认） |
| 前端授权体验 | 审批卡片勾选（删除类自动隐藏该选项，偏好记忆在 localStorage）；【撤销】面板内列出当前授权并可一键取消 | 构建门禁 + 接线断言 |
| 过程可见 | 免打扰执行时推 `notice`：「已授权：精确改脚本 · <文件>（本次任务内不再逐条确认，随时可撤销）」 | 同上 |

> 设计取舍：批量授权之所以现在才做，是因为**必须先有兜底**——写盘有备份与差异统计（第 4 轮）、收尾有改动小结（第 7 轮）、随时可一键撤销（第 5 轮）。没有这三样，批量授权等于把风险放大。

## 十一、第 9 轮（已完成，可验证）：多步任务有进度骨架

复合需求（"检查一遍并修好"、"给战斗加个新机制"）最怕两点：用户不知道 AI 做到哪了、模型做一半跑偏。待办清单同时解决这两件事。

| 交付 | 落点 | 验证方式 |
|---|---|---|
| 清单规整与校验 | `modules/todos.js`：`normalizeTodos()` / `summarizeTodos()` / `validateTransition()` / `renderTodos()` | `tests/test-todos.cjs` 第 1 组：字符串与对象数组、非法项拒绝、上限、统计话术、**进度不可倒退**、纯文本渲染 |
| `todo_write` 工具 | `server.js`（含 `clear`） | 第 2 组：创建 → 推进 → 进度话术 → 禁止倒退 → 全部完成提示可收尾 → 清空 |
| 与小结联动 | `project_changelog` 返回 `todos` / `todoSummary` | 第 3 组：小结带计划与进度、清空后不再带 |
| 过程可见 | 宿主推 `plan` 事件 + `notice`「计划：进度 N/M，正在做：…」 | `tests/test-ai-agent.cjs` 接线断言 |
| 计划卡片 | `ai-agent.js` `renderPlan()`（**同一张卡片原地刷新**）+ `ai-plan` 样式 | 构建门禁 + 接线断言 |

> 细节取舍：进度只允许前进不允许后退（把 `done` 改回 `pending` 会被工具拒绝）——否则用户看到进度倒退会以为出了故障；卡片原地刷新而不是每步新插一张，避免长任务刷屏。

## 十二、第 11 轮（已完成，可验证）：只读工具并发 + 一个隐藏缺陷

**动机**：模型经常在一条消息里请求多个只读工具（一起读几个文件/查几处代码），宿主原来是串行执行的。

**过程中抓到的真缺陷**：宿主自己维护了一份「只读工具清单」副本。副本与 MCP 注册表当前恰好一致（各 18 项），但**将来任何新增的只读工具都会被漏掉**，从而被当成独占调用——并发永远不生效，而看代码完全看不出来。实测证据：到达跨度 802ms（≈ 串行）。

**修法**：以 MCP 注册表的 `readOnlyHint` 为**真源**（工具自己声明是否只读），宿主在 `McpClient.start()` 时拉取一次填充 `declaredReadOnlyTools`；静态清单退化为兜底；未声明/未登记的工具一律按独占处理（宁可慢，也不误并发写操作）。

| 交付 | 落点 | 验证方式 |
|---|---|---|
| 只读并发执行 | `ai-host.js` `isExclusiveCall()` / `runReadOnly()` / 批次合并 | `tests/test-parallel-tools.cjs`：三个 400ms 只读调用**到达跨度 1ms、端到端 418ms**（修复前 802ms / 1222ms） |
| 结果顺序 | 批次内按请求顺序回填 tool 消息 | 同上：`["a","b","c"]` |
| 写盘独占 | 批次在写盘处断开 | 同上第 2 组：混合调用时写盘仍弹审批、之前的只读已完成 |
| 真源接线 | `declaredReadOnlyTools` + `readOnlyHint === true` | `tests/test-ai-agent.cjs` 接线断言 |

> 结论与取舍：修好之后并发确实生效，但要说清收益边界——本项目里 MCP 是同机子进程、只读工具通常几十毫秒返回，**端到端收益有限**；这条改动的真实价值是「消除了一份会腐化的清单副本」，而不是"大幅提速"。
