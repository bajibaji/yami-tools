## 0. 一句话结论（最该补的 3 件事）

1. **对话没有时间轴**——用户消息不能编辑 / 重发 / 从某一轮重来，`/rewind` 等价物在整个仓库 **0 实现**（G-1）。这是最贵的一条：AI 答歪一次，用户要么带着错的上下文继续，要么开新对话重讲一遍需求。最小修法是一个端点（截断 `session.messages`）+ 两个按钮，文件侧复用已有的 `restore_backup` / 【撤销】。
2. **中断的「收尾」还有漏点**——审批续跑阶段不吃取消令牌（那次写盘宿主会继续干等、事件流也拿不到取消回执），而面板侧还有「审批续跑后排队不接力」「等待卡只收尾第一张」（G-5、G-10(a)(b)）。项目自己的铁律 ㊾「点了没反应就是 bug」和 `ai-host.js:2323` 的注释（「只断开界面、后台还在烧 token/改文件，是这类助手最不能接受的坏行为」）说明这是**实现漏了**，不是取舍；修法是 2 行参数 + 2 处几行。
3. **审批缺中间档，且那份自称「唯一对照基准」的文档已经过期**——写盘确认只能「一个工具 × 一个文件」地勾（G-6）；同时 `docs/AI助手-对标ClaudeCode-差距与路线图.md` 的 17 行现状对照里有 2 行与代码不符、另有 6 处过期（S-1~S-6）。前者是 1 个授权键形态的小改动，后者是 6 处文档修正（零风险），单列在 §3.4、**不占 P0 名额**。

### 1.3 t1 的三条判据（本报告判定「差距」的标准）

t1 §0 给的分界线不是功能多少，而是**回路是否闭合**，三条：

1. **中途可干预**——人能在 agent 正在跑的时候施加影响（打断、插话、改权限、改计划），且中断本身不丢弃已完成的工作。（出处：interactive-mode §General controls 的 `Esc` 原文「Claude keeps the work done so far」；§Queue messages while Claude works）
2. **越界前可裁决**——每一次有副作用的动作都能在**动作发生前**被看到并裁决；裁决可记住（本会话/永久）、可撤销；「无论什么模式都必须问」的动作要写清楚。（出处：permission-modes §Available modes、§Actions no mode auto-approves）
3. **事后可定位可撤销**——任意一轮的效果能定位、能回看、能撤销，且**撤销的边界**（撤销不了什么）被明确写出。（出处：checkpointing §How checkpoints work、§Limitations）

本报告 §3 的每条差距都归到这三格之一（见 §3.3），避免退化成功能清单。

#### G-1 消息编辑 / 重发 / 从某一轮分叉重试 —— **最大的结构性缺口**

- **本地锚点**：对 `ai-agent.js`、`ai-host.js` 全量 grep `重新生成|重发|编辑消息|改写|fork|regenerate|resend|rewind|checkpoint|恢复到这一步` → **5 处命中**（`ai-agent.js:13/14/20/296` + `ai-host.js:407`），其中 4 处为无关注释，仅 `296` 是提示文案；**无任何实现**。会话粒度只有整体：`/session/load`(`ai-host.js:2126`)、`/session/delete`(`2142`)、`/clear`(`2302-2316`，只清内容不删文件)。用户消息渲染 `ai-agent.js:489`(`addMessage`) 无任何操作按钮。

- **最小修法**（不新建架构）：宿主加 `POST /session/rewind { sessionId, messageIndex }`：把 `session.messages` 截断到该条用户消息之前并 `saveSession()`（复用现有会话存储与路由写法），把该条文本随响应回填面板输入框；文件侧不需要新机制——`restore_backup`(`server.js:939`) 与面板【撤销】(`ai-agent.js:593`) 已经是逐文件回退。面板在用户消息气泡上加「重发 / 编辑」两颗按钮。**不做**分支树、不做多会话分叉（那是新架构）。

**缺口 1：审批续跑阶段不吃停止信号（真缺陷）**

- `ai-host.js:2289-2291`：`processToolCalls(session, pending.remaining, config, '', events)` —— **第 6 个参数 `cancelToken` 没传**；而 `processToolCalls` 只认自己的 `cancelToken` 形参（`1824`、`1934`），**不读 `events.cancelToken`**。同一路径里被批准的那一次写盘走裸调用 `2251`：`(await ensureMcp()).call(pending.name, args)`，而自动执行路径 `1900`/`1913` 用的是 `callToolWithCancel`（取消即收尾、给出取消回执）。
- 用户可感知后果：用户点了「执行修改」之后再按停止，界面显示「已打断」，但**续跑里的剩余工具调用不会被取消，那一次写盘宿主会一直干等到它返回**（事件流也拿不到取消回执）；若这批里有 `playtest_smoke` 这类长调用（`server.js:986`），用户会以为已经停下。**口径**：这不是「多执行了一次工具」——协议层上那一次写盘本就会跑完（`ai-host.js:1722` 原文：请求已发出、子进程会跑完），差别在**宿主继续干等、缺取消回执**。
- 最小修法：`2290` 补上 `events.cancelToken || null`；`2251` 改用 `callToolWithCancel(client, pending.name, args, events.cancelToken)` —— 改的是**取消能否立刻兑现**（宿主停止干等、事件流给出取消回执），不是「少执行一次工具」。**两行级修复**，不新增机制。
- **同族缺口（t3 §14.4 独立确证，本人复核）**：取消信号还有三处到不了——① 压缩时的摘要模型调用传的是 `null` 令牌（`ai-host.js:443-446`），压缩中途按停止停不住；② 工具请求一旦发出，MCP（stdio 请求-响应协议）没有取消语义，子进程会跑完，宿主只是「不再干等」（原文 `ai-host.js:1719-1727`），迟到的响应被 `onData` 丢弃；③ MCP 侧收到 `notifications/cancelled` 直接忽略（`runtime/yami-mcp/server.js:2032`）。① 是纯漏传（已并入上面的最小修法）；②③ 是协议层限制，要改就得动 MCP 协议，属架构级改动，**不建议本轮动**。
- **优先级**：**P0**（本报告 P0 第 2 项；两行参数 + 一处调用点改写，不新增机制）

**已排除（t5 F5 证伪 + 本人复核）**：早前怀疑「被取消的那条会被记成『未执行』、用户以为工程没动」——**不成立**：

- 在飞的那一条拿到取消回执后（`ai-host.js:1737-1741` → `1913`）**紧接着就被如实记入**（`1915-1916`；纯只读批路径 `1845-1846` → `1852` 同理），`1934` 的补占位会被 `294-306`（`302` 按 `tool_call_id` 去重）跳过。
- 「未执行」只发给**从未开始**的调用（对它们文案是准确的），而且它**不上界面**：`appendUnexecutedToolResults`（`294`）不发 `onTool`，回显用的 `visibleMessages`（`ai-host.js:155-178`，过滤器在 `160-161`）只回放 user/assistant、`role:'tool'` 全部丢弃；在飞那条的取消文案反而是用户可见的（`1928-1930` 的 fail detail）。
- 结论：措辞与账目**不矛盾**，**不需要改代码**（早前「先为 `cancelled === true` 的调用记账」的最小修法已由 `1916` 实现）。
